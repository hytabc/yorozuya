# 02 · 判定引擎规格

> 本文定义因果判定引擎的算法、数据结构、复杂度、调参方法与扩展方式。
> 实现：`src/lib/engine/`；校验：`tools/verify-levels.ts`；测试：`tests/engine.test.ts`。

---

## 一、问题定义

### 1.1 输入输出

```
judgeChain(chain: string[], level: Level, ctx: JudgeContext) → JudgeResult
```

| 参数 | 类型 | 说明 |
|---|---|---|
| `chain` | `string[]` | 完整因果链（碎片 ID 有序数组），长度 = 链长 |
| `level` | `Level` | 关卡定义 |
| `ctx.unlockedEndingIds` | `string[] \| null` | 已解锁结局 ID；`null` = 全部视为已解锁（校验/调试用） |

输出 `JudgeResult` 包含：命中结局、得分、连贯度、情感值、全部结局的评估明细、次优结局。

### 1.2 组合爆炸与对策

可动碎片 n 个 → 排列数 = n!。

| n | 排列数 | 穷举可行性 |
|---|---|---|
| 4 | 24 | ✅ |
| 5 | 120 | ✅ |
| 6 | 720 | ✅ |
| 7 | 5,040 | ✅ |
| 8 | 40,320 | ✅ 仍可接受 |
| 9 | 362,880 | ⚠️ 边界 |

本作单关可动碎片上限为 **7**（9 碎片关卡含 2 个锚点），最大 5,040 种排列，穷举校验完全可行。

**但运行时不能用穷举**——玩家每拖一次都要立即反馈，必须 O(结局数 × 约束数) 完成。

## 二、约束系统

### 2.1 五种约束

| kind | 语义 | 字段 | 匹配条件 |
|---|---|---|---|
| `before` | a 排在 b 之前 | `a`, `b` | `indexOf(a) < indexOf(b)` |
| `adjacent` | a 与 b 相邻（顺序不敏感） | `a`, `b` | `abs(indexOf(a) - indexOf(b)) === 1` |
| `position` | frag 落在第 index 位（0-based） | `frag`, `index` | `indexOf(frag) === index` |
| `block` | a 与 b 相邻（仅用于 anti） | `a`, `b` | 同 `adjacent` |
| `group` | frags 占据连续区间（内部顺序任意） | `frags` | `max(idx) - min(idx) + 1 === frags.length` |

### 2.2 缺失碎片的处理

**任何涉及"链中不存在的碎片"的约束一律返回 `false`，不抛异常。**

这一条至关重要：它让隐藏碎片（如 `frag_1_3_07`）未解锁时，引用它的隐藏结局自动不可命中，无需额外的开关逻辑。

### 2.3 权重语义

| 位置 | 语义 |
|---|---|
| `ending.constraints[].weight` | 满足 → **加** weight |
| `ending.anti[].weight` | 满足 → **减** weight |

### 2.4 数据结构

```ts
interface Constraint {
  kind: 'before' | 'adjacent' | 'position' | 'block' | 'group';
  a?: string;        // before / adjacent / block
  b?: string;        // before / adjacent / block
  frag?: string;     // position
  frags?: string[];  // group
  index?: number;    // position，0-based
  weight: number;
}
```

## 三、评分与判定

### 3.1 单个结局的得分

```
scoreEnding(chain, ending)
  = Σ { c.weight | c ∈ ending.constraints, matchConstraint(chain, c) }
  − Σ { a.weight | a ∈ ending.anti,        matchConstraint(chain, a) }
```

### 3.2 判定主流程

```
judgeChain(chain, level, ctx):

  1. evaluations ← level.endings.map(e => evaluateEnding(chain, e, ctx.unlockedEndingIds))

  2. qualified ← evaluations.filter(e => e.qualified)
       其中 e.qualified = e.unlocked && e.score >= e.threshold

  3. if qualified.isEmpty():
         返回 chaos 结局（isChaos = true）

  4. 排序 qualified：
       主序：score 降序
       次序：约束条数 升序（更"顺其自然"的解法优先）
       末序：endingId 字典序（保证确定性）

  5. 返回 qualified[0]
```

### 3.3 为什么次序是"约束条数更少者优先"

假设两个结局并列同分，一个有 6 条约束、一个有 3 条。前者意味着"必须同时满足 6 个条件"，后者意味着"只需要满足 3 个条件"。

从叙事角度，**约束更少的解更"自然"**——它不需要玩家刻意凑条件。因此并列时让更简洁的解胜出。

### 3.4 复杂度

| 阶段 | 复杂度 |
|---|---|
| `evaluateEnding` | O(C)，C = 该结局的约束数 |
| `judgeChain` | O(E × C)，E = 结局数 |
| 排序 | O(E log E) |
| **总计** | **O(E × C)**，实测 E ≤ 5、C ≤ 6，耗时 < 0.1ms |

远优于性能要求（单次判定 < 5ms）。

## 四、指标计算

### 4.1 因果连贯度 Coherence

```
matchRate(chain, e) = clamp01( scoreEnding(chain, e) / Σ(e.constraints[].weight) )
coherence           = round( 100 × max over e of matchRate(chain, e) )
```

- 取"最接近的结局"的匹配率，保证指标**单调、连续**。
- 不会出现"某个结局满分但连贯度显示很低"的情况。

### 4.2 情感走向 Valence

```
valence = round( 100 × Σ(fragment.valence) / (2 × count) )
```

- 每枚碎片的 `valence ∈ [-2, +2]`；
- 分母 `2 × count` 是理论极值；
- 结果落在 `[-100, +100]`，正值为"靠近"，负值为"疏离"。

### 4.3 结局色调分档

```
valenceBand(ending.valence):
  > +0.2  → 'warm'
  < -0.2  → 'cold'
  其他     → 'neutral'
```

## 五、蝴蝶效应判定

```
detectButterflies(chain, level, alreadyTriggered):
  返回 level.butterflies 中满足
    (1) 不在 alreadyTriggered 中
    (2) requires 中全部约束均匹配
  的全部蝴蝶效应
```

`requires` 中的 `weight` 字段无意义（恒为 1），仅作结构复用。

**辅助函数**：

| 函数 | 作用 |
|---|---|
| `butterflyProgress(chain, butterfly)` | 返回 0..1 的完成度，用于提示系统的方向性引导 |
| `resolveHiddenFragments(level, state)` | 根据存档状态解析应解锁的隐藏碎片 |
| `resolveRedUnlock(chain, level)` | 判断红色碎片是否被解锁 |
| `computeDraggable(chain, level)` | 返回当前可拖拽碎片集合 |

## 六、调参指南

### 6.1 铁律：所有结局满分必须等于 100

**这是本项目最重要的数值约定。**

如果各结局满分不同，`score` 排序就会出现偏差：

```
反例：
  good 满分 70，某排列得 60（匹配率 86%）
  bad  满分 100，同一排列得 65（匹配率 65%）
  → 排序取 score 最高者，bad 胜出。
  → 但显然 good 才是更贴近意图的解读。错误！
```

统一为 100 分后，`score` 即匹配率，排序天然公平。

`tools/verify-levels.ts` 会强制校验这一点，不满足直接报错。

### 6.2 权重分配建议

给定一组约束，权重按"叙事重要性"分配：

| 重要性 | 建议权重 |
|---|---|
| 决定性（缺了就完全不是这个结局） | 30–35 |
| 重要（体现结局核心语义） | 20–25 |
| 辅助（增强区分度） | 15–20 |

四条约束的常见分配：`30 / 25 / 25 / 20`、`35 / 25 / 20 / 20`、`25 / 25 / 25 / 25`。

### 6.3 阈值设定

| 类型 | 阈值 | 说明 |
|---|---|---|
| `true` | 75 | 必须满足绝大部分约束 |
| `good` | 70 | — |
| `bittersweet` | 60 | — |
| `bad` | 55 | 稍容易触发，起警示作用 |

**调整阈值时应先跑 `node tools/verify-levels.ts`**，观察余量与混沌率。

### 6.4 anti 约束的用法

`anti` 用于**排除不该出现的模式**，典型场景：

| 场景 | 写法 |
|---|---|
| 防止两个结局同时高分命中 | 用对方的关键约束做 anti，扣分设为 40–50 |
| 表达"这两件事不该挨在一起" | `{ kind: 'block', a, b, weight: 30 }` |
| 表达"某个碎片不该出现在开头" | `{ kind: 'position', frag, index: 1, weight: 50 }` |

**注意**：anti 的 weight 不参与满分计算，可以自由设置（通常 40–50 足以让另一个结局掉出阈值）。

### 6.5 调参工作流

```
① 写出目标结局的"见证排列"（witness）——一个你希望命中该结局的序列
② 为每条见证排列写 4 条约束，权重凑够 100
③ 检查该见证排列是否"顺带"满足其他结局的约束
   ├─ 是 → 给其他结局加 anti
   └─ 否 → 继续
④ node tools/verify-levels.ts <关卡ID>
⑤ 若某结局不可达 → 放宽其约束或降低阈值
⑥ 若混沌率 > 65% → 整体降低阈值 5 分
⑦ 若混沌率 < 30% → 整体提高阈值 5 分
```

### 6.6 常见问题排查

| 症状 | 原因 | 解决 |
|---|---|---|
| 结局 A 不可达 | A 的约束被 B 的 anti 覆盖，或约束之间自相矛盾 | 检查 A 的见证排列是否满足 A 的全部约束；检查 B 的 anti 是否误伤 |
| 两个结局总是同分 | 约束语义重叠 | 给其中一个加 anti |
| 混沌率过高 | 阈值太严 | 阈值 −5 |
| 某排列同时满足 3 个结局满分 | 约束区分度不足 | 给每个结局加一条独占约束 |

## 八、全局结局判定

终章 4-3 结算后，由 `global-endings.json` 决定最终的全局结局。

```
GlobalScore = 100 × ( 0.4 × levelScore
                    + 0.2 × goodCount
                    + 0.2 × trueCount
                    + 0.2 × bondMean )

levelScore = judgeChain(chain_4_3).score / 100
goodCount  = min(已达成 good 结局数, 9) / 9
trueCount  = min(已达成 true 结局数, 10) / 10
bondMean   = (mean(bond.Mio, bond.Shiori, bond.Rin) + 100) / 200
```

| GlobalScore | 全局结局 |
|---|---|
| ≥ 85 | `global_true`「欢迎回来」（真结局） |
| ≥ 65 | `global_good`「重新开始」（Happy End） |
| ≥ 40 | `global_bittersweet`「远处的灯」 |
| < 40 | `global_bad`「无人登入」 |

**覆盖规则（优先级最高）**：若同时满足

- 4-3 链中 `adjacent(frag_4_3_08, frag_4_3_07)` 且 `before(frag_4_3_08, frag_4_3_05)`
- 且"放手类"结局数 ≥ 3（`3_2_true`、`4_2_good`、`4_2_true` 中至少 3 个）

则强制命中 `global_give_away`「把世界交给你」。

**设计意图**：真结局不应由单一关卡的高分换得，而应由一整段旅程累积而成。因此 60% 的权重压在全局变量上。

## 九、扩展方式

### 9.1 新增一种约束

1. 在 `types.ts` 的 `ConstraintKind` 加入新字面量；
2. 在 `constraints.ts` 的 `matchConstraint` switch 中实现分支；
3. 在 `tools/verify-levels.ts` 的 `validateLevel` 中加入字段校验（若有新字段）；
4. 更新本文档 §2.1 表格与 `docs/06-数据字典.md`。

**注意**：新约束必须遵守"碎片不存在则返回 false"的约定，否则隐藏碎片会误命中。

### 9.2 新增关卡

1. 在 `src/lib/data/levels/` 新建 `<id>.json`；
2. 在 `levels/index.json` 注册；
3. 运行 `node tools/verify-levels.ts <id>` 直到全绿；
4. 运行 `node --test tests/engine.test.ts` 确认数据完整性用例通过。

### 9.3 调整判定策略

`judge.ts` 中的排序逻辑是集中在一处的。若将来想改成"按匹配率排序"而非"按得分排序"，只需改 `qualified.sort()` 的比较函数——在 100 分制下两者等价，但若将来放开满分约束，就需要切到 `matchRate` 排序。
