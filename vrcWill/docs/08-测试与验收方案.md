## 二、数据校验器（verify-levels）

### 2.1 它做什么

对每个关卡**枚举全部合法排列**（保留首尾锚点），回答四个问题：

1. 每个设计结局是否至少被一种排列命中？
2. 每个结局的最优排列与得分余量？
3. 混沌兜底占比是否落在 30%–65%？
4. 数据是否自洽？

### 2.2 自检项

| 检查 | 级别 |
|---|---|
| 碎片 ID 无重复 | 错误 |
| 锚点存在且 `type === 'gray'` | 错误 |
| `initialOrder` 首尾 = 锚点 | 错误 |
| `initialOrder` 无重复、无未知碎片 | 错误 |
| 可动区间内无灰色碎片 | 错误 |
| 约束引用的碎片必须存在于本关 | 错误 |
| `position` 约束必须有 `index` | 错误 |
| `threshold ≤ Σ(constraints.weight)` | 错误 |
| 同关卡各结局 `Σ(constraints.weight)` 相等 | 错误 |
| 结局 ID 无重复 | 错误 |

### 2.3 当前结果（基线）

```
总计：12 关，设计结局 45 项（去重后），可达 45 项。
全部关卡校验通过。
```

**这是回归基线。任何一次改动后，这个数字都必须保持 45/45。**

> 注：校验器对 1-3 会跑两个配置（基础 / 解锁隐藏碎片），未去重时会显示 48 项。去重后为 45 项，这是全作**关卡内设计结局**的真实数量。

### 2.4 混沌率基线

| 关卡 | 排列数 | 混沌数 | 占比 | 判定 |
|---|---|---|---|---|
| 1-1 | 24 | 13 | 54.2% | ✅ |
| 1-2 | 120 | 62 | 51.7% | ✅ |
| 1-3（基础） | 120 | 35 | 29.2% | ✅ |
| 1-3（解锁） | 720 | 185 | 25.7% | ⚠️ 略低于 30% |
| 2-1 | 120 | 52 | 43.3% | ✅ |
| 2-2 | 720 | 214 | 29.7% | ⚠️ 略低于 30% |
| 2-3 | 120 | 58 | 48.3% | ✅ |
| 3-1 | 720 | 324 | 45.0% | ✅ |
| 3-2 | 120 | 61 | 50.8% | ✅ |
| 3-3 | 5040 | 2580 | 51.2% | ✅ |
| 4-1 | 720 | 450 | 62.5% | ✅ |
| 4-2 | 720 | 297 | 41.3% | ✅ |
| 4-3 | 5040 | 2803 | 55.6% | ✅ |

> 1-3 与 2-2 略低于 30% 是**可接受的**：这两关的约束区分度高，大部分排列都能落到某个结局上，这是设计意图（它们都是"信息量密集"的关卡）。若后续希望提高混沌率，可将阈值各 +5。

## 三、单元测试用例矩阵

当前 **34 项**，全部通过。

### 3.1 约束匹配器（9 项）

| 用例 | 断言 |
|---|---|
| `before` 命中 / 未命中 | — |
| `adjacent` 顺序不敏感 | `A,B` 与 `B,A` 均命中 |
| `position` 为 0-based 完整链下标 | 含锚点的下标 |
| `block` 等价于 `adjacent` | — |
| `group` 连续区间 | `[B,C]` ✓；`[A,C]` ✗；顺序任意 ✓ |
| 引用不存在碎片一律 `false` | `before` / `position` / `group` |
| 畸形约束不抛异常 | 缺字段、空数组 |
| `assembleChain` 首尾锚点 | — |

### 3.2 评分（5 项）

| 用例 | 断言 |
|---|---|
| 得分 = 满足约束之和 − anti 扣分 | — |
| **各关卡所有结局满分一致且 = 100** | 12 关全查（铁律） |
| 阈值不超过理论最高分 | — |
| `valence` 落在 -100..100 | — |
| `coherence` 落在 0..100 | — |

### 3.3 判定主流程（8 项）

| 用例 | 断言 |
|---|---|
| 2-3 推荐解命中 `good`，得分 100 | 且 `isExactSolution` 为真 |
| 2-3 隐藏解命中 `true`，得分 100 | — |
| 未命中任何结局时走混沌 | `isChaos` 时 `ending.type === 'chaos'` |
| 判定幂等 | 同一输入两次结果一致 |
| `requires` 未满足时不可命中 | 锁定 / 解锁对比 |
| `isEndingUnlocked` 三态语义 | `null` / `[]` / `['x']` |
| `evaluateEnding` 轨迹长度 | = 约束数 + anti 数 |
| `previewChain` 稳定态标记 | 满分排列 `settled === true` |

## 五、手动验收清单

### 5.1 手感（每关必过）

- [ ] 拖拽跟手，无延迟感
- [ ] 落位动画干脆，不拖沓
- [ ] 非法落点回弹自然
- [ ] 指标条变化与操作直觉一致
- [ ] 长链（9 碎片）滚动流畅

### 5.2 文案

- [ ] 碎片正文通顺，无错别字
- [ ] 「」使用正确，无英文引号
- [ ] 无过度文学化表达
- [ ] 结局文本情绪到位，不煽情
- [ ] 提示文案不泄露答案

### 5.3 叙事

- [ ] 四个章节的情感曲线成立
- [ ] 关键呼应能被玩家察觉（如 1-3 ↔ 4-2 的「嗯」）
- [ ] 3-2 的"放手"设计可被感知
- [ ] 4-1 的身份揭示不突兀

### 5.4 视觉

- [ ] 12 关卡片颜色均可区分
- [ ] 五种碎片类型视觉区分明显
- [ ] 五种结局色调区分明显
- [ ] 无明显视觉噪音

## 七、回归清单（每次改动后必跑）

```bash
# 1. 数据校验（最重要）
node tools/verify-levels.ts
#    期望：总计 12 关，设计结局 45 项（去重后），可达 45 项；全部关卡校验通过

# 2. 单元测试
node --test tests/engine.test.ts
#    期望：tests 34, pass 34, fail 0

# 3. 类型检查（需先 npm install）
npm run typecheck
#    期望：无错误

# 4. 构建
npm run build
#    期望：成功，首包 < 300KB gzip
```

### 7.1 改动影响速查

| 改动类型 | 必须重跑 |
|---|---|
| 编辑关卡 JSON | 1 + 2 |
| 修改引擎逻辑 | 1 + 2 + 3 |
| 修改 `types.ts` | 1 + 2 + 3 + 4 |

## 八、缺陷分级

| 级别 | 定义 | 示例 | 处理时限 |
|---|---|---|---|
| **P0 阻塞** | 无法通关 / 数据丢失 | 某结局不可达、存档写入失败 | 立即 |
| **P1 严重** | 核心体验受损 | 拖拽失效、结局展示错误 | 当次迭代 |
| **P2 一般** | 影响体验但不阻塞 | 动画卡顿、配色不协调 | 下个迭代 |
| **P3 轻微** | 细节问题 | 文案错别字、间距不齐 | 择机 |

## 九、自动化建议

### 9.1 提交前 hook

```json
// package.json
"scripts": {
  "precommit": "node tools/verify-levels.ts && node --test tests/engine.test.ts"
}
```

### 9.2 CI 流程（GitHub Actions）

```yaml
name: verify
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '22' }
      - run: node tools/verify-levels.ts
      - run: node --test tests/engine.test.ts
      - run: npm ci
      - run: npm run typecheck
      - run: npm run build
```

> 前两步**不需要 `npm install`**——引擎零依赖，这是把它写成纯 TS 模块的直接收益。
