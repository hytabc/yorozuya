## 1. 一页结论

### 1.1 主线

> **授权 → 快照 → 披露 → 沉淀**

1. 用户自愿绑定 VRChat 身份，服务端拉取并归一化信任信号；
2. 数据以“快照”形式缓存，明确标注来源与时间，不伪装成官方认证；
3. 用户逐项决定对谁披露什么，委托双方在点击之前就能看到有据可依的信息；
4. 委托完成后，完成记录沉淀为可展示、可导出的凭证与作品集标签。

### 1.2 五个工作层与优先级

| 优先级 | 工作层 | 核心动作 | 建议阶段 | 是否阻塞后续 |
|---|---|---|---|---|
| P0 | 身份层 | VRChat 身份绑定、信任快照、逐项披露、信任徽章 | 阶段 1 | 是 |
| P1 | 浏览层（轻） | 委托卡片模块化、技能/平台/World 标签、筛选 | 阶段 2 | 是 |
| P1 | 准入层 | “委托礼仪确认”替代文本免责墙、预设氛围标签 | 阶段 2 | 否 |
| P2 | 完成层 | 委托凭证、创作者作品集、反向生成标签、识人记录 | 阶段 3 | 否 |
| P3 | 浏览层（空间化） | Three.js 星图/走廊浏览，作为可选视图 | 阶段 4 | 否 |
| P4 | 实时层 | 站内事件流、VRChat 通知、OSC 本地桥接 | 阶段 5，按需 | 否 |

### 1.3 为什么按这个顺序

- **先有可信数据，再谈展示**：没有身份层，模块化卡片和凭证都只是装饰。
- **先做轻量模块化，再做 3D**：卡片数据结构稳定后，空间化视图只是同一批数据的另一种渲染方式；反过来会反复返工。
- **凭证依赖完成数据**：必须先把委托完成、确认、快照逻辑做扎实，凭证才是不可篡改的履历，而不是一张可随意生成的图片。
- **实时层最后做**：VRChat WebSocket 与 OSC 的稳定性和合规风险最高，且不是“信任感”的必要条件。

## 2. 现状与差距

### 2.1 当前实现

| 能力 | 现状 | 相关文件 |
|---|---|---|
| 委托大厅 | 列表 + 筛选，卡片为标题、描述、分类、状态、人数等平面信息 | `frontend/src/views/TaskHall.vue`、`frontend/src/components/TaskCard.vue` |
| 委托详情 | 弹窗展示委托与接单人，支持接取/确认/取消 | `frontend/src/components/TaskDialog.vue` |
| 用户资料 | 昵称、简介、QQ、头像、称号、介绍图片；无 VRChat 身份字段 | `backend/app/models.py`、`frontend/src/components/UserProfileCard.vue` |
| VRChat 相关 | 仅有交友厅的 `vrc_nickname` 文本字段，无 API 集成 | `backend/app/models.py`、`main.py` 的 `/api/friends/*` |
| 完成记录 | 只有状态与计数，没有凭证、作品集或结构化评价 | `Task.status`、`TaskMember.confirmed_at` |
| 免责声明 | 以长文本形式出现在进入之后 | 前端相关页面与静态文案 |
| 3D 能力 | 房屋模块已使用 Three.js，具备场景、相机、交互与测试先例 | `frontend/src/house/`、`backend/app/house.py` |
| 后端 HTTP 客户端 | 已有 `httpx==0.28.1`，无需新增依赖 | `backend/requirements.txt` |
| 前端 3D 依赖 | 已有 `three@^0.185.1`，无需新增依赖 | `frontend/package.json` |

### 2.2 关键差距

1. **没有可验证的 VRChat 身份锚点**：用户填写的 VRChat 昵称无法证明账号归属，也无法展示信任等级、账号年龄或社交关系。
2. **委托信息不可结构化**：技能栈、平台要求、参考 World 都混在自由文本里，无法筛选、聚合或反向生成标签。
3. **完成记录不可携带**：完成数只是站内数字，不能导出、不能作为创作者履历展示。
4. **准入缺少设计**：免责声明是法律文本，不是交往伦理；用户在进入前没有建立“这是一个彼此尊重的创作者空间”的心智。
5. **网站与 VRChat 本体没有双向感知**：站内状态变化无法触达用户的 VRChat 侧，VRChat 侧的通知也无法进入站内。

## 3. 设计原则与非目标

### 3.1 设计原则

1. **不伪造信任**
   - 所有 VRChat 数据必须标注“由本人授权同步自 VRChat”和同步时间。
   - 不使用“官方认证”“平台担保”“实名认证”等措辞。
   - 数据过期、解绑、API 失败时明确显示“已过期/未同步”，而不是继续展示旧值。

2. **最小披露**
   - 默认只展示完成委托所必需的信息，其余逐项开关。
   - 共同好友只展示数量或“有/无”，不下发原始好友列表。
   - Group 只展示双方共同所在或本人主动选择的公开 Group，不导出完整成员关系。
   - 匿名委托不得泄露发布者的 VRChat 身份，即使发布者已绑定。

3. **服务端代理，浏览器不碰凭证**
   - VRChat 的会话令牌、Cookie、2FA 信息只允许存在于服务端。
   - 前端只接收归一化后的展示字段，不接触 VRChat SDK 的认证对象。
   - 不使用浏览器直连 VRChat API，避免 CORS、CSP 与令牌泄露问题。

4. **快照优于实时**
   - 拉取结果落库为快照，设置 TTL 与手动刷新冷却。
   - VRChat API 不可用时，页面优雅降级，不阻塞委托主流程。
   - 任何依赖 VRChat 的功能都必须有“未绑定/未同步”的完整降级路径。

5. **氛围先于功能**
   - 准入层的摩擦必须携带意义，而不是增加无意义的点击。
   - 法律免责声明不能删除，但可以后移、折叠，并用一屏人能读完的“礼仪确认”作为前台。

6. **保持轻量**
   - 不引入新的重型前端框架；空间化视图复用现有 Three.js。
   - 新路由继续使用 `() => import()` 动态导入。
   - 新功能全部带服务端/前端开关，默认关闭或灰度开启。

### 3.2 非目标

- 不做完整的 VRChat 客户端，不在站内浏览 World、聊天或管理好友。
- 不自动发送好友申请、不接受好友申请、不代替用户执行 VRChat 社交动作。
- 不把 VRChat 登录作为本站唯一登录方式；本站账号体系不变。
- 不承诺“平台担保交易”或“身份绝对真实”。
- 不在第一阶段做完整 3D 世界漫游；只做轻量 2.5D 星图/走廊。
- 不在第一阶段做 OSC 反向提示；服务端无法直接向用户本机的 VRChat 客户端发送 OSC。
- 不把 VRChat 密码写入数据库；不持久化不必要的会话凭证。

## 4. 总体架构

### 4.1 架构选择

VRChat.js 是 TypeScript SDK，适合作为**接口契约与类型参考**，但不建议直接在浏览器里运行：

- 浏览器直连会把 VRChat 凭证暴露给前端；
- VRChat API 的 CORS、Cookie、2FA 流程不适合纯前端；
- 现有 CSP 严格限制第三方脚本，引入 SDK 需要放宽策略，得不偿失。

推荐方案：

```
Vue 前端
  └─ /api/vrchat/*  ──►  FastAPI 适配层  ──►  VRChat Web API
                           │
                           ├─ 认证与会话（服务端）
                           ├─ 归一化与快照（SQLite）
                           ├─ 披露策略（逐项开关）
                           └─ 限流、缓存、降级
```

- 后端新建独立模块 `backend/app/vrchat/`，不要继续把逻辑堆进 `main.py`：
  - `client.py`：基于 `httpx` 的最小 REST 适配器，接口字段以 VRChat.js 的类型定义和预研结果为准。
  - `auth.py`：绑定会话、状态校验、挑战码、令牌处理。
  - `normalize.py`：Trust Rank、账号年龄、平台、Group、World、好友关系的归一化。
  - `service.py`：快照读写、TTL、披露策略、共同好友计算。
  - `routes.py`：`/api/vrchat/*` 路由，挂到 `main.py`。
- 前端新建：
  - `frontend/src/components/VrTrustBadge.vue`：紧凑信任徽章。
  - `frontend/src/components/TrustDisclosureDialog.vue`：逐项披露设置。
  - `frontend/src/composables/useVrchatTrust.js`：状态、缓存、错误降级。
  - `frontend/src/constants.js`：信任等级、技能、平台、氛围标签的显示名与颜色。

### 4.2 数据流

```
用户点击“绑定 VRChat”
  → 服务端创建一次性 LinkSession（state + 过期时间）
  → 用户在 VRChat 侧完成授权/挑战
  → 回调校验 state、一次性消费
  → 服务端拉取 profile / friends / groups / worlds
  → 归一化后写入 VRChatSnapshot
  → 展示预览，用户逐项确认披露范围
  → 写入 VRChatIdentity.disclosure_json
  → 委托卡片/详情按披露策略读取快照
```

### 4.3 失败与降级

| 场景 | 行为 |
|---|---|
| 用户未绑定 | 不显示信任徽章；显示“未绑定 VRChat”中性提示，不视为负面 |
| 绑定过期/令牌失效 | 显示“授权已过期，点击重新绑定”；保留历史快照但标注过期 |
| VRChat API 限流 | 使用缓存快照；超过 TTL 显示“上次同步于 X”；不自动重试风暴 |
| 用户关闭全部披露 | 对他人完全隐藏；本人仍可在设置中看到自己的数据 |
| 匿名委托 | 强制隐藏发布者信任信息，接口层直接不返回 |
| 功能开关关闭 | 前后端均不渲染入口；已有数据保留但不展示 |

## 5. 方向一：身份信任层（P0）

### 5.1 绑定方式

| 方案 | 说明 | 建议 |
|---|---|---|
| A. OAuth / 官方开放平台 | 用户跳转 VRChat 授权，本站不接触密码 | **首选**，但需预研当前开放范围与申请条件 |
| B. 一次性挑战码 | 用户在 VRChat 个人资料/状态中放置本站生成的一次性码，服务端校验 | **降级方案**，不接触密码，适合 OAuth 不可用时 |
| C. 用户名密码 + 2FA | 兼容性最好，但本站需要处理并保护用户 VRChat 凭证 | **不作为默认**；除非有明确安全评审与加密方案 |
| D. 仅手动填写 | 用户自报 Trust Rank/账号年龄 | **不采用**，无法防伪造，反而制造虚假信任 |

预研阶段必须回答：

- 当前可用的认证方式、是否需要 2FA、令牌有效期与刷新机制；
- 能稳定获取哪些字段：Trust Rank、账号创建时间、平台、Group、好友、World；
- 速率限制、错误码、封禁策略；
- VRChat 服务条款对第三方站点展示这些数据的要求；
- 是否允许服务端长期保存会话凭证；若不允许，改为“短会话 + 不持久化令牌”。

> **重要约束**：如果预研发现只能通过保存用户密码/长期 Cookie 才能工作，则身份层降级为“一次性挑战 + 手动刷新快照”，不做后台常驻同步。信任感不能以保存用户密码为代价。

### 5.2 绑定流程（推荐版本）

1. 用户在“个人设置 → VRChat 身份”点击绑定。
2. 服务端创建 `VRChatLinkSession`：
   - `state` 为高熵随机值，唯一索引；
   - TTL 10 分钟，一次性消费；
   - 记录发起用户、发起 IP 摘要（不存原文）、创建时间。
3. 用户完成 OAuth 或挑战码验证。
4. 服务端校验：
   - `state` 存在、未过期、未使用、属于当前用户；
   - 挑战码匹配且未被使用；
   - 拉取到的 VRChat 用户 ID 未被其他本站账号占用。
5. 服务端拉取并归一化数据，写入快照。
6. 前端展示“将公开哪些字段”的预览，用户逐项确认后保存。
7. 绑定成功后，个人资料页出现“VRChat 身份”模块；委托卡片开始显示信任徽章。

### 5.3 解绑与数据删除

- 解绑立即：
  - 删除或作废服务端保存的 VRChat 令牌；
  - 将 `VRChatIdentity.status` 置为 `unlinked`；
  - 删除原始快照中的社交关系数据；
  - 保留已签发的委托凭证，但凭证上标注“身份来源已解绑”，不撤回历史完成事实。
- 用户可单独请求“删除我的 VRChat 数据”，彻底删除身份与快照；已公开的凭证页面保留凭证编号与完成事实，但不显示 VRChat 身份。
- 监管台提供“全局关闭 VRChat 集成”开关，用于 API 故障、合规要求或安全事件。

### 5.4 字段与归一化

| 字段 | 来源 | 展示方式 | 披露默认 | 备注 |
|---|---|---|---|---|
| Trust Rank | VRChat 用户 `tags` 中的 `system_trust_*` | 五档徽章：Visitor / New User / User / Known User / Trusted User | 关闭 | 未知标签归 `unknown`，不自行发明等级 |
| 账号年龄 | 账号创建时间 | “账号年龄 3 年 2 个月” | 关闭 | 存原始时间戳，展示时计算 |
| 平台 | 用户资料中的平台标记 | PCVR / Quest / Desktop 图标 | 关闭 | 以 VRChat 返回为准，缺失则不显示 |
| Group | 用户加入的 Group | 共同 Group 名称或“有共同社群” | 关闭 | 默认只展示双方共同且公开的 Group |
| 好友关系 | 好友列表 | “有共同好友”或共同好友数量 | 关闭 | 必须双方都绑定且都开启；不返回原始列表 |
| 常驻 World | 最近活动/公开数据，或用户手动选择 | World 名称/封面，最多 3 个 | 关闭 | 若 API 无可靠数据，退化为手动选择，不伪造 |

**Trust Rank 映射表**放在后端 `normalize.py` 与前端 `constants.js` 两处，必须同步；未知标签统一显示“未识别”，不猜测。字段名以预研结果为准，本文不锁定具体 JSON key。

### 5.5 共同好友与共同 Group 的计算

- 只有以下条件全部满足才计算：
  1. 双方都已完成绑定；
  2. 双方都开启“共同好友/共同社群”披露；
  3. 当前请求者已登录，且不是匿名委托的另一方。
- 计算在服务端完成，只返回聚合结果：
  - 共同好友数 `0 / 1 / 2 / 3+`，或“有共同好友”；
  - 共同 Group 只返回双方都加入且公开的 Group 名称，最多 3 个。
- 原始好友 ID、Group 成员列表在计算后立即丢弃，不写入响应、不写入日志。
- 对匿名委托，即使双方有共同好友，也不展示任何发布者侧信息。

### 5.6 展示位置

| 位置 | 展示内容 | 交互 |
|---|---|---|
| `TaskCard` | 发布者信任徽章（等级 + 账号年龄），最多一行 | 点击卡片进入详情；徽章 hover/tap 显示来源与同步时间 |
| `TaskDialog` | 发布者完整信任模块；接单人列表中每人一行信任摘要 | 点击“查看信任详情”打开侧栏/弹窗 |
| `UserProfileCard` | 信任模块 + 作品集入口 | 沿用现有资料弹窗 |
| `FriendHall` | 可选显示 VRChat 昵称与信任等级 | 由用户披露开关控制 |
| `CreatorPortfolio` | 信任模块固定在头部 | 见方向三 |

视觉上保持克制：徽章只承担“快速判断”，不堆叠图标；详情里再解释数据来源、时间和含义。

### 5.7 接口设计

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/vrchat/status` | 登录 | 返回当前用户绑定状态、同步时间、披露设置 |
| POST | `/api/vrchat/link/start` | 登录 | 创建一次性绑定会话 |
| GET | `/api/vrchat/link/callback` | 公开回调 | 校验 state，完成绑定 |
| POST | `/api/vrchat/link/challenge` | 登录 | 挑战码模式的校验入口 |
| POST | `/api/vrchat/refresh` | 登录 | 手动刷新快照，带冷却 |
| POST | `/api/vrchat/unlink` | 登录 | 解绑并清理凭证 |
| PATCH | `/api/vrchat/disclosure` | 登录 | 逐项更新披露开关 |
| DELETE | `/api/vrchat/data` | 登录 | 删除本人 VRChat 数据 |
| GET | `/api/users/{user_id}/trust` | 登录 | 按披露策略返回信任摘要 |
| GET | `/api/tasks/{task_id}/trust` | 登录 | 返回委托双方的信任摘要，匿名委托强制裁剪 |
| GET | `/api/admin/vrchat/status` | 管理员组 | 查看集成开关、失败率、过期数量（不返回用户社交数据） |
| PATCH | `/api/admin/vrchat/config` | 超管 | 全局开关、同步 TTL、是否允许新绑定 |

限流桶建议：

- `vrchat-link`：用户，5 次 / 3600 秒；
- `vrchat-refresh`：用户，10 次 / 3600 秒；
- `vrchat-trust-read`：用户，120 次 / 600 秒；
- `vrchat-callback`：IP，30 次 / 600 秒。

错误文案统一中文，例如“绑定链接已过期，请重新发起”“VRChat 暂时不可用，已展示上次同步的数据”。

### 5.8 数据模型

```text
VRChatIdentity
  id, user_id (unique), vrchat_user_id (unique),
  display_name, trust_rank, account_created_at,
  disclosure_json, status, link_method,
  linked_at, last_synced_at, last_error

VRChatSnapshot
  id, identity_id, kind, payload_json,
  fetched_at, expires_at
  index (identity_id, kind, fetched_at)

VRChatLinkSession
  id, user_id, state (unique), method,
  challenge_hash, expires_at, used_at, created_at
```

- `payload_json` 只存归一化后的展示字段，不存原始好友列表、Group 成员列表、会话 Cookie。
- 新表由 `create_all` 创建；若后续给 `users` 或已有表加列，必须在 `migrate_schema()` 补 `ALTER`，并注意该函数中 tasks 的提前 `return`，把用户相关迁移放在它之前。
- 不在 ORM 模型上添加 `vrchat_avatar_url` 之类的派生属性，避免绕过披露策略；所有 URL/展示字段由 `present_*` 函数生成。

## 6. 方向二：委托卡片模块化与空间化浏览（P1 / P3）

### 6.1 模块化卡片（P1）

#### 6.1.1 目标

把“一份建模委托”从一行标题，变成一组可筛选、可聚合、可复用的模块：

- 技能栈：Blender / Unity / PhysBones / lilToon / Udon / VRChat SDK / 灯光 / 世界优化 / Quest 兼容 / 音频 / 其他；
- 期望平台：PCVR / Quest / Desktop / 不限；
- 参考 World：最多 3 个，可关联现有地图推荐或填写 World 名称/链接；
- 委托类型：沿用现有 `TASK_CATEGORIES`；
- 报酬方式：沿用 `pay_type`、`reward`；
- 氛围标签：沟通方式、节奏、边界、是否可录制/二次创作；
- 发布者信任摘要与完成记录。

#### 6.1.2 数据结构

推荐新增 `TaskFacet`，而不是把标签塞进自由文本：

```text
TaskFacet
  id, task_id, facet_type, value, sort, created_at
  unique (task_id, facet_type, value)
  index (facet_type, value)
```

`facet_type` 第一版支持：

- `skill`：技能；
- `platform`：平台；
- `world`：参考 World；
- `atmosphere`：氛围标签；
- `tool`：工具/插件（可与 skill 合并，第一版保留扩展位）。

不新增 `Task` 大字段，避免 SQLite 迁移与查询复杂度；筛选走 `TaskFacet` 索引。

技能与平台的词表放在：

- 后端：`backend/app/main.py` 或独立 `vrchat` 模块中的白名单常量；
- 前端：`frontend/src/constants.js`。

两边必须同步，参照现有 `TASK_CATEGORIES` 与 `CATEGORIES` 的维护方式。创建/编辑委托时做白名单校验，非法值返回 422。

#### 6.1.3 接口变更

| 方法 | 路径 | 变更 |
|---|---|---|
| GET | `/api/tasks` | 增加 `skill`、`platform`、`world`、`atmosphere` 查询参数；返回 `facets` |
| GET | `/api/tasks/{id}` | 返回 `facets`、`publisher_trust`、`completion_summary` |
| POST | `/api/tasks` | 接收 `facets` 数组，校验白名单与数量上限 |
| PATCH | `/api/tasks/{id}` | 允许委托人在未开始前调整 facets |
| GET | `/api/tasks/facets` | 返回可用词表与计数，供筛选器使用 |

性能注意：

- 列表查询用 `selectinload(Task.facets)` 或批量查询，避免 N+1；
- 筛选与分页沿用现有约定，`page`/`page_size` 默认 20、上限 50；
- 旧委托没有 facets 时，接口返回空数组，前端隐藏模块，不阻塞展示。

#### 6.1.4 前端改造

- `CreateTaskDialog.vue`：新增“技能与平台”步骤/区块，使用 chips 选择，不强制填写；参考 World 支持从 `VrMaps` 选择或手动输入。
- `TaskCard.vue`：展示 2–3 个技能 chip、平台图标、发布者信任徽章；保持现有卡片高度可控，超出折叠为“+N”。
- `TaskDialog.vue`：完整模块列表，按“需求 / 技能 / 平台 / 参考 World / 氛围 / 发布者信任 / 完成记录”分组。
- `TaskHall.vue`：筛选栏增加技能、平台、氛围；保留现有分类、状态、有偿/无偿筛选。
- 空态文案从“没有找到相关委托”改为更符合空间语汇的提示，例如“这片区域暂时没有符合条件的委托”，并提供“清除筛选 / 发布一份委托”两个动作。

### 6.2 空间化浏览（P3，可选视图）

#### 6.2.1 定位

空间化浏览是**列表的补充视图**，不是替代品：

- 默认仍是列表，保证可访问性、性能和移动端可用；
- 用户可切换“列表 / 星图”；
- 星图只渲染当前筛选结果的前 60 条，避免一次加载全部；
- 点击卡片打开现有 `TaskDialog`，不新建一套详情逻辑。

#### 6.2.2 技术方案

- 复用现有 `three@^0.185.1`，参考 `frontend/src/house/` 的场景、相机、交互与测试替身做法。
- 新增 `frontend/src/hall/space/`：
  - `HallSpaceCanvas.vue`：Three.js 画布；
  - `layout.js`：按分类/技能分簇的确定性布局，纯函数、可测试；
  - `useHallSpace.js`：相机、缩放、拖拽、选中状态；
  - `HallSpaceView.vue`：列表/星图切换壳。
- 视觉：
  - 2.5D 等距或轻微透视，不做自由飞行；
  - 委托卡片以 billboard 形式悬浮，文本用 HTML overlay 保证清晰与可选中；
  - 连线表示同技能/同 World/同发布者，不表示交易关系；
  - 背景使用克制的深色星图，不堆粒子特效。
- 交互：
  - 拖拽平移、滚轮/双指缩放、点击选中、双击打开；
  - 键盘：Tab 在卡片间移动，Enter 打开，Esc 关闭；
  - `prefers-reduced-motion` 下禁用自动浮动与镜头缓动；
  - 移动端限制像素比与卡片数量，必要时自动回退列表。
- 性能预算：
  - 星图 chunk 懒加载，首次进入再加载 Three.js；
  - 首屏 JS 增量不超过约 200 KB gzip（以构建分析为准）；
  - 60 张卡片以内保持交互流畅；超出提示“缩小范围或切换列表”。

#### 6.2.3 阶段门

空间化视图在以下条件满足后再启动：

- 身份层与模块化卡片已上线并稳定；
- 委托大厅的筛选使用率、卡片点击率有可观测数据；
- 至少完成一次移动端与低性能设备的手动验收；
- 产品侧确认“星图”不会成为唯一入口。

建议用配置开关 `HALL_SPACE_VIEW` 控制，默认关闭，灰度给部分用户。

## 7. 方向三：完成凭证与创作资本（P2）

### 7.1 目标

让每一次完成都沉淀为接单者可以带走、可以展示的资产，同时给委托方留下“识人记录”，形成双向信誉，而不是单向的“平台不担保”。

### 7.2 委托凭证

#### 7.2.1 生成时机

- 委托进入 `completed` 状态时，在完成确认的同一事务中，为每位接单人生成一张凭证。
- 幂等：`unique (task_id, taker_id)`；重复确认不会生成第二张。
- 凭证内容在生成时快照，后续修改委托标题、技能、发布者资料都不影响历史凭证。

#### 7.2.2 凭证内容

| 字段 | 说明 |
|---|---|
| 凭证编号 | `WS-{年份}-{6 位序号}`，不含用户 ID |
| 委托标题 | 生成时快照 |
| 委托类型 | 分类 |
| 技能栈 | 从 `TaskFacet` 快照 |
| 平台 | PCVR / Quest / Desktop / 不限 |
| 委托方 | 非匿名时显示昵称与签章；匿名时显示“匿名委托” |
| 接单人 | 昵称与（可选）VRChat 身份摘要 |
| 完成时间 | `Task.completed_at` |
| 签发时间 | 凭证生成时间 |
| 来源说明 | “基于本站完成记录生成，可在站内验证编号” |

#### 7.2.3 展示与导出

- 前端 `CredentialCard.vue` 使用 Canvas 2D 绘制，参考 `frontend/src/vrclife/components/VrShareCard.vue` 的导出方式，输出 1200×1600 PNG。
- 凭证页 `/credential/:serial`：
  - 公开/仅链接/私有三档；
  - 服务端返回结构化 JSON，前端渲染；
  - 页面包含验证说明与“举报伪造”入口；
  - 不依赖用户上传图片，避免 SVG/XSS 与审核负担。
- 第一版不做服务端生成 PNG，也不做可嵌入的 SVG badge；等公开页稳定后再评估。
  - 若后续要做 SVG badge，必须使用固定模板、转义所有文本、设置 `Content-Security-Policy: default-src 'none'; sandbox`，并经过安全评审。
- 分享：复制链接、下载 PNG、分享到常用平台；不自动发到 VRChat。

#### 7.2.4 防伪造

- 凭证编号由数据库自增 ID 生成，`serial` 唯一索引；
- 公开页由服务端按编号查询，不存在即 404；
- 页面明确写“本站可验证的是完成记录，不是 VRChat 官方认证”；
- 监管台可撤销凭证（例如确认刷单、虚假委托），撤销后公开页显示“已失效”，不物理删除历史。

### 7.3 创作者作品集

#### 7.3.1 反向生成标签

- 不提供“自己选擅长标签”的入口，避免自我包装。
- 从已完成委托的 `TaskFacet` 聚合：
  - 某技能完成次数 ≥ 2 才生成标签；
  - 标签显示“建模 · 5 次完成”“World 灯光 · 3 次完成”；
  - 保留最近一次完成时间与证据链接（委托详情，按可见性裁剪）。
- 用户可以选择隐藏某个标签，但不能手动新增或修改计数。
- 第一版聚合在读取时计算，数据量大后再加缓存表 `UserPortfolioTag`。

#### 7.3.2 个人主页

新增 `/creators/:userId`（或复用 `/u/:userId`，落地时二选一）：

- 头部：昵称、称号、简介、信任徽章、作品集标签；
- 凭证墙：按时间倒序，支持按技能筛选；
- 完成记录：只展示公开字段，匿名委托显示“匿名委托”；
- 联系方式：沿用现有 QQ 可见性规则；
- 入口：`UserProfileCard`、委托详情接单人列表、凭证页作者链接。

不修改现有 `/profile` 的定位：它仍是本人设置页；`/creators/:id` 是对外展示页。

### 7.4 识人记录（可选，阶段 3.5）

委托方需要“哪些接单者完成了、完成质量如何”。建议第一版只做轻量结构化评价，不做公开自由文本：

```text
TaskReview
  id, task_id, from_user_id, to_user_id,
  rating (1-5), badges_json, private_note,
  created_at
  unique (task_id, from_user_id, to_user_id)
```

- 只有委托进入 `completed` 后才可评价；
- 评价双方各一次，互不可见对方的具体分数，直到双方都提交或 7 天后；
- `badges_json` 使用固定词表：专业、守时、沟通顺畅、交付完整；
- `private_note` 仅被评价人本人与管理员可见，不公开展示；
- 公开页只展示聚合分与徽章次数，不展示单条评价；
- 管理员可处理恶意评价；评价入口与文案必须避免引导刷分。

如果评审认为评价体系过重，可先只做“完成记录 + 凭证”，把 `TaskReview` 留到有明确需求后再做。

### 7.5 接口设计

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/credentials/mine` | 登录 | 本人凭证列表 |
| GET | `/api/credentials/{serial}` | 按可见性 | 凭证详情 |
| PATCH | `/api/credentials/{serial}/visibility` | 本人 | 公开/仅链接/私有 |
| GET | `/api/creators/{user_id}` | 公开 | 作品集聚合 |
| GET | `/api/creators/{user_id}/credentials` | 公开 | 凭证墙分页 |
| POST | `/api/tasks/{task_id}/reviews` | 登录 | 提交评价（可选阶段） |
| GET | `/api/users/{user_id}/reviews/summary` | 登录 | 评价聚合（可选阶段） |
| PATCH | `/api/admin/credentials/{id}` | 管理员组 | 撤销/恢复凭证 |

凭证可见性必须在服务端校验，不能只靠前端隐藏。

## 8. 方向四：氛围准入（P1）

### 8.1 定位

不是“加一个年龄弹窗”，而是用一层轻量的前置仪式，把平台的调性在进入之前建立起来。

同时必须保留完整法律免责声明：

- 前台展示一屏可读完的“委托礼仪确认”；
- 完整条款移到 `/terms`，在确认页提供“查看完整说明”；
- 不删除、不弱化法律文本，只是改变呈现顺序与语言。

### 8.2 触发范围

| 场景 | 是否触发 | 说明 |
|---|---|---|
| 首次进入委托大厅 | 是 | 可关闭后继续浏览 |
| 首次发布委托 | 是 | 必须确认后才能提交 |
| 首次接取委托 | 是 | 必须确认后才能接取 |
| 公告/条款版本更新 | 是 | 版本号变化后重新确认 |
| 浏览其他页面 | 否 | 不打扰 |
| 已确认用户再次进入 | 否 | 按账号记录；游客按浏览器本地记录 |

### 8.3 文案草案

> **这里不担保交易，但这里记录信誉。**
>
> 请只发布你真正需要帮助的事，只接下你真正能完成的事。
>
> 尊重对方的时间、劳动与边界。遇到分歧，先沟通，再决定是否继续。
>
> [ 我明白，进入委托大厅 ]　[ 查看完整说明 ]

按钮不做“同意/拒绝”的法律化措辞，改成“进入/先看看”；完整条款仍可访问。

### 8.4 预设氛围标签

在发布委托时，用 chips 让发布者进入“我在一个彼此尊重的创作者空间里”的心智，而不是“我在一个免责论坛里发帖”：

| 维度 | 选项 |
|---|---|
| 沟通方式 | 文字为主 / 语音沟通 / 游戏内沟通 |
| 节奏 | 轻松推进 / 紧凑交付 / 可长期协作 |
| 边界 | 可录屏 / 不录屏 / 可二次创作 / 不可二次创作 |
| 报酬 | 有偿 / 无偿 / 以物易物 / 可协商 |
| 期望 | 新手友好 / 需要经验 / 可指导 |

这些标签进入 `TaskFacet` 的 `atmosphere` 类型，可筛选，但不参与权限或排序权重。

### 8.5 数据与接口

- 登录用户：`AtmosphereAck(user_id unique, version, accepted_at)`；
- 游客：`localStorage` 记录版本号，不落库；
- `GET /api/atmosphere/status` 返回当前版本与是否已确认；
- `POST /api/atmosphere/ack` 记录确认；
- 版本号常量前后端同步，建议放在 `constants.js` 与后端配置/常量中各一份，并在发布说明中标注。

### 8.6 设计要求

- 全屏或半屏遮罩，深色半透明，文字逐句出现，动效克制；
- 焦点陷阱、Esc 可关闭（浏览场景）、键盘可操作；
- `prefers-reduced-motion` 下取消文字动画；
- 移动端可滚动，不遮挡“查看完整说明”；
- 不使用强制倒计时、不能跳过的长动画；摩擦要有意义，不是折磨。

## 9. 方向五：实时层（P4，按需）

### 9.1 先做站内事件流

在接入 VRChat WebSocket 之前，先把站内状态变化做成可订阅的事件：

- 新委托、接取、开始、待确认、完成、取消、举报处理、审核结果；
- 复用现有邮件通知的触发点，抽象 `TaskEvent`；
- 前端先做通知中心，再评估 SSE（`/api/events/stream`）或轮询；
- 默认不引入 WebSocket 服务，避免运维复杂度。

### 9.2 VRChat 通知

若身份层已能稳定维持服务端会话，可评估：

- 服务端订阅 VRChat WebSocket，接收好友请求/通知；
- 只映射事件类型与时间，不保存消息正文；
- 用户可关闭；
- 连接失败、限流、封禁时静默降级，不影响站内功能。

风险：

- VRChat WebSocket 非官方稳定契约，接口变更会导致功能失效；
- 每个用户一条长连接会带来资源与运维压力；
- 需要严格的退避、去重、熔断与告警。

**结论**：不作为第一版目标；等站内事件流稳定、用户明确需要后再做。

### 9.3 游戏内 OSC 提示

必须明确架构事实：

- 服务端**不能**直接向用户本机的 VRChat 客户端发送 OSC；
- OSC 是本地 UDP，通常由用户机器上的程序发送到 VRChat；
- 若要实现“站内委托状态触发游戏内提示”，需要用户安装一个本地桥接器（companion app），由它轮询/订阅站内事件并发送 OSC。

因此建议：

- 第一阶段只做站内通知 + 邮件；
- 若社区确实需要，再做一个可选的、开源的本地桥接器，单独文档与安全说明；
- 不在网页里承诺“自动触发游戏内提示”。

## 10. 分阶段路线图

> 以下用“阶段门”而不是工期描述；每个阶段完成后必须通过验收再进入下一阶段。

### 阶段 0：技术预研与合规确认

**目标**：在不写用户功能的前提下，确认 VRChat 集成可行、合规、可控。

交付物：

- `docs/vrchat-api-notes.md`：认证方式、可用字段、速率限制、错误码、ToS 要点；
- 一份最小 `httpx` 调用脚本（只读、手工运行、不部署）；
- 风险清单与降级方案；
- 是否引入持久化令牌的结论。

退出标准：

- 明确首选认证方式与降级方式；
- 明确第一版可稳定获取的字段；
- 明确“不保存密码”的底线；
- 安全与合规评审通过。

### 阶段 1：身份信任层

范围：

- 绑定/解绑/刷新/删除数据；
- 信任快照与 TTL；
- 逐项披露；

## 11. 数据模型与迁移清单

| 表 | 用途 | 创建方式 | 关键约束 |
|---|---|---|---|
| `vrchat_identities` | 本站账号与 VRChat 身份的绑定 | `create_all` | `user_id` 唯一、`vrchat_user_id` 唯一 |
| `vrchat_snapshots` | 归一化信任快照 | `create_all` | `(identity_id, kind, fetched_at)` 索引 |
| `vrchat_link_sessions` | 一次性绑定会话 | `create_all` | `state` 唯一、`expires_at` |
| `task_facets` | 委托技能/平台/World/氛围标签 | `create_all` | `(task_id, facet_type, value)` 唯一；`(facet_type, value)` 索引 |
| `task_credentials` | 完成凭证 | `create_all` | `(task_id, taker_id)` 唯一、`serial` 唯一 |
| `user_portfolio_tags` | 作品集标签缓存（可选） | `create_all` | `(user_id, tag)` 唯一 |
| `atmosphere_acks` | 礼仪确认记录 | `create_all` | `user_id` 唯一 |
| `task_reviews` | 结构化评价（可选） | `create_all` | `(task_id, from_user_id, to_user_id)` 唯一 |

迁移注意：

- 新表由 `create_all` 自动创建，不需要 `ALTER`；
- 若给 `users` 加列（例如 `vrchat_identity_id`），必须在 `migrate_schema()` 中、tasks 提前 `return` 之前补 `ALTER`；
- 所有 `ALTER` 用 `if "column" not in columns` 守卫，保证幂等；
- 不在 ORM 模型上添加会绕过可见性/披露策略的派生 URL 属性；
- 所有新上传/生成的媒体文件走 `media.write_media` / `media.media_url` / `media.delete_media`，不手写路径；
- 凭证第一版不落盘图片，避免媒体审核与存储负担；若后续落盘，必须走媒体 helper 与审核流程。

## 14. 安全、隐私与合规清单

### 14.1 必须通过

- [ ] 不保存 VRChat 密码；不以密码作为默认绑定方式。
- [ ] VRChat 令牌不进入浏览器、不写入日志、不写入前端缓存。
- [ ] 若持久化令牌，必须服务端加密；加密密钥只放 `.env`，不写入仓库。
- [ ] 披露开关在服务端强制执行，前端隐藏不等于接口安全。
- [ ] 共同好友/Group 只返回聚合结果，不返回原始列表。
- [ ] 匿名委托在接口层裁剪发布者信任信息，不能只靠前端。
- [ ] 解绑/删除数据后，原始快照与令牌被清理。
- [ ] VRChat API 失败不影响委托发布、接取、确认、取消主流程。
- [ ] 所有新接口挂 `get_current_user` 或明确的 `get_optional_user`，不绕过邮箱闸门。
- [ ] 新增限流桶，避免绑定/刷新接口被刷。
- [ ] 新增埋点事件必须加入 `EVENT_LABELS` 白名单，不记录 VRChat ID 或社交关系。
- [ ] 凭证页面不渲染用户上传的 SVG/HTML；文本全部转义。
- [ ] 若引入任何第三方脚本或客户端 SDK，必须同步更新 `frontend/nginx.conf` 的 CSP。
- [ ] 完成一次针对“越权读取他人信任数据”的专项测试。

### 14.2 合规与条款

- 预研阶段阅读并记录 VRChat 服务条款对第三方应用、数据展示、自动化的限制；
- 不提供批量抓取、自动加好友、自动发消息等能力；
- 站内文案明确“数据由本人授权同步，可能滞后，不构成平台担保”；
- 提供用户数据导出/删除路径；
- 若 VRChat 要求应用审核或特定署名，按对方要求执行。

### 14.3 运维与熔断

- `VRCHAT_ENABLED` 全局开关，默认关闭，预研通过后开启；
- `VRCHAT_ALLOW_NEW_LINKS` 控制是否接受新绑定；
- 监控：绑定成功率、快照过期数、API 错误率、限流触发次数；
- 熔断：连续失败达到阈值时暂停自动刷新，只保留手动重试；
- 回滚：关闭开关后，前端隐藏入口，后端保留数据但不展示，不影响主流程。

## 16. 验收标准

### 16.1 身份层

- 未绑定用户看不到任何 VRChat 信任信息，也不会被负面标记；
- 绑定流程不能被重放、跨账号使用或绕过 state 校验；
- 用户关闭某项披露后，他人接口立即返回空；
- 共同好友只在双方都绑定且都开启时出现，且只返回聚合值；
- 匿名委托不泄露发布者 VRChat 信息；
- 解绑后原始社交数据被清理，凭证保留但标注来源已解绑；
- VRChat 不可用时，委托主流程不受影响。

### 16.2 浏览层

- 旧委托无 facets 时正常展示；
- 技能/平台筛选结果准确；
- 卡片在桌面与移动端都不溢出、不遮挡操作；
- 星图视图与列表使用同一数据源，筛选结果一致；
- 星图可键盘操作，reduced-motion 下无自动动画；
- 低性能设备可回退列表。

### 16.3 完成层

- 完成委托后自动生成凭证，重复确认不重复生成；
- 凭证内容不可被后续编辑篡改；
- PNG 可下载，公开页可访问，私有页不可越权访问；
- 作品集标签只来自完成记录，用户不能自选；
- 撤销凭证后公开页显示失效；
- 匿名委托凭证不显示发布者身份。

### 16.4 准入层

- 首次进入大厅出现礼仪确认，可关闭后浏览；
- 首次发布/接取前必须确认；
- 版本升级后重新触发；
- 游客确认记录只存本地；
- 完整法律条款仍可从确认页访问；
- 键盘、移动端、reduced-motion 可用。

### 16.5 非功能

- 新路由全部懒加载，星图 chunk 不进入首屏；
- 新增接口有明确限流与中文错误文案；
- 新增表在旧库启动时自动创建，无需手工迁移；
- 无新增未评审依赖；
- 安全清单全部通过。

## 17. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| VRChat API 非官方、接口变更 | 身份层失效 | 适配层隔离、快照缓存、全局开关、失败降级 |
| 认证流程复杂/2FA 摩擦 | 绑定转化低 | 优先 OAuth；提供挑战码降级；明确“不绑定也能正常使用” |
| 用户不愿交密码 | 信任层无法推进 | 永不把密码作为默认方案；必要时只做一次性校验 |
| 信任等级被误读为“官方认证” | 误导与纠纷 | 文案明确来源与时间；不使用“认证/担保”措辞 |
| 共同好友/Group 泄露隐私 | 用户反感、合规风险 | 默认关闭、双方同意、只返回聚合值、可删除数据 |
| 匿名委托泄露身份 | 严重信任事故 | 接口层强制裁剪；专项测试；匿名与身份披露互斥 |
| 3D 视图性能差/眩晕 | 体验下降 | 2.5D、默认列表、卡片上限、reduced-motion、回退 |
| 凭证被伪造/刷单 | 信誉体系失真 | 编号服务端验证、撤销机制、举报入口、评价风控 |
| 评价体系引发刷分/报复 | 社区矛盾 | 先只做完成记录；评价双方互盲、固定词表、管理员处理 |
| 实时层运维复杂 | 稳定性下降 | 先站内事件流；VRChat WebSocket 后置；OSC 只做本地桥接 |
| 新依赖/CSP 变更 | 安全面扩大 | 复用现有 `httpx`/`three`；不引入客户端 VRChat SDK；CSP 变更需评审 |
| 旧数据迁移出错 | 启动失败 | 幂等 ALTER、迁移前备份、测试覆盖旧库场景 |

## 18. 待决策问题

以下问题需要在阶段 0 或阶段 1 开始前确认：

1. **品牌**：对外是否切换为 coldrain？本文按“本站”落地，品牌切换只影响文案与配置。
2. **认证方式**：VRChat OAuth 是否可用？若不可用，是否接受“一次性挑战码 + 手动刷新”的降级体验？
3. **默认披露**：绑定后默认全关，还是默认开启「Trust Rank + 账号年龄」并提示用户可关闭？建议默认全关，但在绑定完成页推荐开启这两项。
4. **凭证默认可见性**：默认“仅链接”还是“公开”？建议默认“仅链接”，用户主动公开。
5. **评价体系**：第一版是否包含 `TaskReview`？建议先只做完成记录与凭证，评价作为阶段 3.5。
6. **空间化视图**：是否确认只做可选视图、默认列表？建议是。
7. **实时层**：是否接受“OSC 需要本地桥接器”的事实？若不接受，实时层只做站内通知。
8. **数据保留**：解绑后原始快照立即删除，还是保留 30 天供审计？建议立即删除聚合数据，审计日志只保留事件类型与时间。
