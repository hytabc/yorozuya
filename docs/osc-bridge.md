# 游戏内 OSC 提示：为什么需要本地桥接器

> 本文说明「站内委托状态 → VRChat 游戏内提示」的架构事实，以及将来若要做本地桥接器
> 需要注意什么。**当前版本不提供桥接器程序**，站内只做通知中心 + 邮件。
> 最后更新：2026-11

## 1. 架构事实

OSC 是**本机 UDP**：

```
[本站服务器] --(HTTP 轮询/订阅)--> [用户电脑上的桥接器] --(UDP 9000)--> [VRChat 客户端]
```

- 服务端**不能**直接向用户本机的 VRChat 客户端发送 OSC：中间隔着用户的家用网络与 NAT。
- VRChat 只在**本机**监听 OSC 端口，通常由 `127.0.0.1:9000` 接收。
- 因此"站内状态触发游戏内提示"必然需要用户在本地运行一个程序。

## 2. 因此本站不做的事

- 不在网页里承诺"自动触发游戏内提示"。
- 不把"实时层"的第一版建立在 OSC 上；先做站内事件流与通知中心（已实现）。
- 不在服务端保存任何 VRChat 会话，去驱动"服务端反向推送"（见 `vrchat-api-notes.md`）。

## 3. 如果社区确实需要，桥接器应该长什么样

建议做成**独立开源小工具**，而不是塞进本站仓库：

1. 用户在自己的电脑上运行，粘贴「本站个人访问令牌」（不是账号密码）。
2. 轮询 `GET /api/events/summary`（或将来新增的 `GET /api/events/pending`）。
3. 收到新事件后发送 OSC 参数，例如 `/chatbox/input`：
   - 只发送事件类型与委托标题（**不发送正文、不发送 QQ、不发送对方昵称**）；
   - 频率上限建议 1 条/10 秒，避免刷屏。
4. 本地保存"已提示过的事件 id"，避免重复。
5. 失败时静默重试，不影响游戏。

安全要求：

- 令牌只存在本地配置文件，权限 0600；不写日志。
- 不自动下载/执行任何远端内容。
- 不实现"自动加好友""自动发消息"等站内没有的能力。

## 4. 与站内事件流的关系

站内事件流已经覆盖：指定委托、接取、开始、待确认、完成、取消请求、取消、被隐藏。
桥接器只需要消费同一批事件，不需要新接口——但**不建议**现在就把 `/api/events` 的响应结构
冻结成桥接器契约，等真的有人做桥接器时再单独设计一个只读、可长轮询的接口。
