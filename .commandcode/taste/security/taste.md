# Taste
- Requires authorization/permission checks to be enforced server-side; treats client-side role checks (localStorage user, locally-decoded JWT, JS-visible permission flags) as a vulnerability to be removed, not trusted. Confidence: 0.92
- Wants security risks hunted down and fixed in a comprehensive full sweep across the whole project rather than one issue at a time. Confidence: 0.65
- Willing to accept infrastructure/architecture-level hardening as part of security work (defense-in-depth), not just application-code fixes — when given a scoped choice, opts into the broadest tier including controlled/unauthenticated-upload access, container non-root user, read-only rootfs, and dropped capabilities. Confidence: 0.5
- Treats privacy of user personal information (accounts, profiles, user-uploaded photos) as a first-class security concern, not only classic injection bugs like XSS. Confidence: 0.5
- Objects to storing sensitive data (auth tokens, user info) in plaintext in browser localStorage; wants client-side credentials encrypted, and prefers an insecure-fallback-free degrade (memory-only) over ever writing plaintext. Confidence: 0.85
- Wants human verification (captcha) on login AND registration, and wants the verification mechanism designed as a pluggable/config-switchable provider so third-party captcha services can be dropped in later. Confidence: 0.8
- Wants persistent-login ("自动登录"/remember-me) convenience, but only with a bounded hard expiry on the token (e.g., must not be usable after 7 days) — convenience must not mean indefinite sessions. Confidence: 0.6
- Objects to real production identifiers (e.g. the live domain name) being hardcoded anywhere in the repo; wants them supplied only via an env config file so pushing to GitHub carries no privacy risk. Confidence: 0.75
- Never wants private identifiers (real domain names, ICP filing numbers, emails, keys) recorded in taste entries or any tracked file — public examples must use generic placeholders like example.com. Confidence: 0.9
- Expects a strict credential-handling routine when handing over third-party service secrets: real value only in the gitignored `.env`, placeholders/`${VAR:-}` references in `.env.example`/compose/docs, an explicit check that no git-tracked file contains the value, and a flag that anything pasted into the conversation should be rotated. Confidence: 0.7
- When a security control conflicts with convenience, picks the stricter control and accepts the UX friction: mandatory email verification before new signups can log in and forced email binding for pre-existing accounts — over the softer "remind only" / "allow but warn" options. Counter-evidence: later had the email one-time code second login factor removed entirely to stop consuming SMTP quota, so the stricter-control instinct yields when the control burns a scarce/paid resource. Confidence: 0.5
- Prefers least privilege for internal operational data: the operations console's analytics dashboard should be invisible to the mascot (看板娘) role and readable only by the admin group (super admin + staff). Confidence: 0.5
- Wants security-assessment results delivered as a written Markdown document committed into the repo (e.g. a Chinese-named findings list such as `问题清单.md`) — a severity-ranked issue list, not just a chat summary. Confidence: 0.5
- Treats that written findings document as a standing work order: a terse follow-up like "修复问题清单中的所有问题" means the agent should resolve every listed item in one pass (high through low severity), not pick a subset. Confidence: 0.55
- Asks for a project's security posture as an explicit scored assessment — a numeric score with a letter grade and per-dimension subscores — written up as an in-repo Markdown report, with re-assessments extending the same audit document as a dated section rather than replacing it. Confidence: 0.55
- Wants the assessment to cover the deployed instance as well as the source: supplies the deployed URL (e.g. the development-environment address) in the request and expects external passive checks — response headers, TLS, unknown-Host handling, path traversal, docs/schema exposure, dependency audit — alongside the code audit. Confidence: 0.6
- Wants checks against the live site kept non-destructive: scoped to passive observation, explicitly no active penetration testing, no writes to production accounts and no load/stress testing. Confidence: 0.5
